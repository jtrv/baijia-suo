Benchmarking and Static Analysis Plan

A project-specific tool recommendation for baijia-suo, a Rust Wayland screen locker with a large animation library, raw shared-memory rendering, PAM/IPC boundaries, and deliberate unsafe code.

Recommended stack Rust MSRV 1.86 Never launch the locker from automation Prepared 2026-07-20

Safety constraint

Benchmark and analysis commands must operate on library code, test targets, benchmark targets, or an already-running owner-started process. They must not invoke cargo run, cargo flamegraph against the default binary, or execute target/*/baijia-suo. A failed locker session can prevent the owner from regaining the desktop.

Recommended stack

1 / benchmark harness

Criterion 0.8.2

Use for stable, repeatable microbenchmarks of AnimationPlayer, simulation ticks, rendering, and buffer copies. Criterion stores statistical baselines and reports confidence intervals instead of relying on single timings.

Version 0.8 raised its MSRV to Rust 1.86, exactly matching this project. The benchmark target runs independently and does not start Wayland or PAM.

2 / real workload profiler

Linux perf, attached by PID

Use perf stat and perf record against a lock session started by the owner. This measures the compositor-facing workload, memory traffic, cache behavior, and hot stacks that isolated microbenchmarks cannot reproduce.

Prefer direct perf attachment over cargo flamegraph, whose normal workflow launches the selected binary.

3 / required static check

Clippy with warnings denied

Keep the existing all-target check mandatory. Clippy's default groups cover correctness, suspicious code, complexity, style, and common performance mistakes with no additional project dependency.

RUSTC_WRAPPER= cargo +stable clippy \
  --all-targets --locked -- -D warnings
4 / unsafe-code validation

Miri, narrowly targeted

This repository has unsafe allocation, pointer slicing, mmap, alignment, fork/pipe, PAM, and Wayland FFI. Miri can detect undefined behavior in code paths it can emulate, including out-of-bounds access, invalid alignment, use-after-free, and aliasing violations.

Use test filters. Whole-suite Miri is a poor fit because several OS and FFI operations are unsupported or prohibitively slow.

5 / supply chain

cargo-deny

Use one policy tool for RustSec advisories, license allowlists, duplicate crate bans, and trusted dependency sources. Until configured, the already-installed cargo audit remains a useful advisory-only check.

6 / test quality

cargo-llvm-cov

Use source-based coverage to find unexercised rendering policies, buffer lifecycle branches, parser validation, and safe wrappers around unsafe code. Coverage is diagnostic evidence, not a percentage target.

Criterion benchmark design

The smallest useful suite is one benchmark target with a representative mode matrix. The public animation API already exposes AnimationPlayer, so no benchmark-only production abstraction is needed.

Manifest shape

[dev-dependencies]
criterion = "0.8.2"

[[bench]]
name = "animations"
harness = false

Use std::hint::black_box, Criterion throughput in bytes for copies, and a fixed amount of setup outside the timed loop. Keep HTML reports optional; numeric baselines are sufficient for review and CI artifacts.

Owner-run profiling protocol

Counter sample

perf stat -p "$PID" \
  -e task-clock,cycles,instructions,cache-misses \
  -- sleep 30

Record the active mode, resolution, scale, FPS cap, commit, CPU governor, and whether the indicator was active.

Hot-stack sample

perf record -g -p "$PID" -- sleep 30
perf report

For meaningful Rust symbols, profile an optimized build with debug information enabled in a dedicated profiling Cargo profile. Do not weaken the shipped release profile.

Use the existing --debug-timing reports beside perf. Criterion establishes repeatable component deltas; perf and the internal logger establish whether those deltas matter in a real Wayland session.

Tools not worth adopting now

iai-callgrind

Useful for deterministic instruction-count regressions in pure algorithms, but it is a poor primary model for this project's memory bandwidth, cache effects, SIMD copies, and compositor-facing behavior. Add only if Criterion proves too noisy for a specific tick algorithm.

cargo-nextest

The current suite is small and already finishes quickly. Parallel test infrastructure adds little, and Miri specifically retains some race-detection advantages with the standard test runner.

cargo-udeps

Already installed, but nightly-only and redundant for routine use. Keep it only as confirmation when cargo-machete reports a questionable dependency.

cargo-bloat and cargo-llvm-lines

cargo bloat --release --crates is useful if shipped binary size becomes a goal. LLVM line counts diagnose compile-time monomorphization, not animation runtime performance. Neither belongs in the initial optimization loop.

Mutation testing and fuzzing

Potentially useful for parsers and IPC later, but neither answers the current rendering-performance question. Add a focused fuzzer only when a concrete untrusted-input boundary lacks effective examples.

Automated cargo-flamegraph launch

Rejected for the application binary because it could start the screen locker. It remains acceptable against a named benchmark target, or its underlying perf workflow can attach to an owner-started PID.

Adoption order

  1. Add one Criterion benchmark target. Establish advance, blit, and combined baselines for five modes at three resolutions.
  2. Profile one owner-run session with perf. Compare Petri and binaryring at 3440x1440 against the existing timing logs.
  3. Add cargo-deny policy. Keep Clippy, rustfmt, tests, and dependency policy as the routine CI gate.
  4. Run targeted Miri and sanitizer passes. Prioritize raw buffers, allocation, alignment, mmap ownership, and IPC serialization.
  5. Generate coverage only after those checks. Use uncovered risk paths to select tests rather than enforcing an arbitrary percentage.

Questions for external review

  • Does the proposed benchmark matrix isolate simulation, canonical rendering, and SHM-copy cost without changing production visibility solely for benchmarks?
  • Which modes best represent each RenderPolicy, and are any selected modes too nondeterministic for reliable Criterion comparisons?
  • Is Criterion 0.8.2's dependency footprint acceptable as a dev-only dependency under the project's minimal-dependency policy?
  • Which unsafe modules can Miri exercise without disabling isolation or masking unsupported OS behavior?
  • What objective threshold should justify item 16b direct-to-SHM complexity: absolute frame time, memory bandwidth, CPU utilization, or battery impact?
